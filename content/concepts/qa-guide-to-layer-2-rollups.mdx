# A QA's Guide to Layer 2s: What's Different About Testing Rollups?

If you've been testing smart contracts on Ethereum mainnet, you're probably familiar with the workflow: deploy a contract, write tests, run them against Hardhat's local network or a testnet, and you're done. But when you move to Layer 2 (L2) networks like Optimism, Arbitrum, or Base, **everything changes**.

L2s promise speed and low costs—transactions that cost $50 on mainnet now cost pennies, and they confirm in seconds instead of minutes. But this magic comes with a price: **complexity**. Testing an L2 dApp isn't just testing a smart contract anymore. You're now testing a **multi-chain system** with bridges, sequencers, batch submissions, challenge periods, and entirely new failure modes that don't exist on L1.

This guide will walk you through the new mental models and testing strategies you need to effectively QA applications on Layer 2 rollups.

---

## Why L2s Are Different: The Architectural Shift

Before diving into testing strategies, let's understand what makes L2s fundamentally different from Ethereum mainnet.

### The L2 Stack

When your dApp runs on an L2, it's not just running on one blockchain—it's running on a **stack of components**:

**1. The L2 Execution Layer** (Optimism, Arbitrum, etc.)
- Where your smart contracts live
- Where users submit transactions
- Fast and cheap, but not immediately final

**2. The Sequencer**
- Orders and executes transactions
- Often centralized (single point of failure)
- Provides "soft confirmations" in seconds

**3. The Batch Submission System**
- Periodically posts transaction data to Ethereum L1
- This is where security comes from
- Operates on a different timescale (minutes to hours)

**4. The Bridge Contracts**
- L1 contracts that lock/unlock assets
- L2 contracts that mint/burn wrapped assets
- The most critical attack surface

**5. The Challenge System** (Optimistic Rollups only)
- 7-day window where anyone can challenge invalid state
- Adds massive delays to withdrawals
- Must be tested with time manipulation

### The Testing Implication

On Ethereum mainnet, your test environment is a single blockchain. On L2, **your test environment must simulate the entire stack**—or you're not really testing your dApp's behavior in production.

## The #1 Risk: Testing the Bridge

Let's be blunt: **the bridge is where the money gets stolen**.

Look at the biggest hacks in crypto history:
- **Ronin Bridge**: $625 million stolen
- **Poly Network**: $611 million stolen
- **Wormhole Bridge**: $325 million stolen
- **Nomad Bridge**: $190 million stolen

Bridges are the most critical and most vulnerable component of any L2 system. As a QA, **testing bridge operations is your highest priority**.

### Understanding Bridge Mechanics

A bridge enables asset transfers between L1 (Ethereum) and L2 (Optimism/Arbitrum/Base). Here's how it works:

**Deposits (L1 → L2):**
1. User locks tokens in the L1 bridge contract
2. L1 bridge emits a `DepositInitiated` event
3. L2 listens for this event and mints equivalent tokens on L2
4. User receives L2 tokens (usually within minutes)

**Withdrawals (L2 → L1):**
1. User burns tokens on L2
2. L2 bridge emits a `WithdrawalInitiated` event
3. Transaction data is batched and posted to L1
4. **7-day challenge period** (Optimistic Rollups only)
5. User can finalize withdrawal on L1
6. L1 bridge releases the locked tokens

The asymmetry is critical: **deposits are fast, withdrawals are slow**.

## Testing Deposits (L1 → L2): The "Easy" Part

Deposits are relatively straightforward because they're fast and don't involve the challenge period.

### What You're Testing

Your test must verify:
1. ✅ Tokens are locked in the L1 bridge contract
2. ✅ Corresponding tokens are minted on L2
3. ✅ The amounts match exactly
4. ✅ The correct recipient receives the tokens
5. ✅ Events are emitted correctly

### The Test Strategy

You'll need to run tests that interact with **both L1 and L2 simultaneously**. Here's the pattern:

```javascript
describe('Bridge Deposits (L1 -> L2)', () => {
  it('should deposit tokens from L1 to L2', async () => {
    // 1. Setup: Deploy bridge contracts on both chains
    const l1Provider = new ethers.providers.JsonRpcProvider(L1_RPC);
    const l2Provider = new ethers.providers.JsonRpcProvider(L2_RPC);
    
    const l1Bridge = await ethers.getContractAt('L1Bridge', L1_BRIDGE_ADDRESS, l1Provider);
    const l2Bridge = await ethers.getContractAt('L2Bridge', L2_BRIDGE_ADDRESS, l2Provider);
    
    const user = await ethers.getSigner();
    const depositAmount = ethers.utils.parseEther('100'); // 100 tokens
    
    // 2. Record initial balances
    const l1BalanceBefore = await token.balanceOf(user.address);
    const l2BalanceBefore = await l2Token.balanceOf(user.address);
    
    // 3. Approve and deposit on L1
    await token.connect(user).approve(l1Bridge.address, depositAmount);
    
    const depositTx = await l1Bridge.connect(user).depositERC20(
      token.address,
      l2Token.address,
      depositAmount,
      200000, // L2 gas limit
      ethers.constants.AddressZero // no data
    );
    
    // 4. Wait for deposit to be relayed to L2
    // This uses the L2 SDK to wait for the message to be relayed
    const receipt = await depositTx.wait();
    const [messageHash] = await l1Bridge.getMessageHash(receipt);
    
    // Wait for L2 to process the deposit (can take 1-5 minutes)
    await waitForMessageStatus(messageHash, MessageStatus.RELAYED);
    
    // 5. Verify L1 state
    const l1BalanceAfter = await token.balanceOf(user.address);
    expect(l1BalanceAfter).to.equal(l1BalanceBefore.sub(depositAmount));
    
    // 6. Verify L2 state
    const l2BalanceAfter = await l2Token.balanceOf(user.address);
    expect(l2BalanceAfter).to.equal(l2BalanceBefore.add(depositAmount));
    
    console.log('✅ Deposit successful: L1 tokens locked, L2 tokens minted');
  });
  
  it('should revert deposit if insufficient balance', async () => {
    const excessiveAmount = ethers.utils.parseEther('1000000');
    
    await expect(
      l1Bridge.connect(poorUser).depositERC20(
        token.address,
        l2Token.address,
        excessiveAmount,
        200000,
        ethers.constants.AddressZero
      )
    ).to.be.revertedWith('Insufficient balance');
  });
  
  it('should emit correct events on both chains', async () => {
    const depositTx = await l1Bridge.depositERC20(/* ... */);
    const receipt = await depositTx.wait();
    
    // Check L1 event
    const l1Event = receipt.events.find(e => e.event === 'ERC20DepositInitiated');
    expect(l1Event).to.exist;
    expect(l1Event.args.amount).to.equal(depositAmount);
    
    // Check L2 event (after relay)
    const l2Receipt = await waitForL2Transaction(messageHash);
    const l2Event = l2Receipt.events.find(e => e.event === 'DepositFinalized');
    expect(l2Event).to.exist;
  });
});
```

### Key Testing Considerations for Deposits

**Gas Limits**
- L2 transactions have gas limits specified by the L1 depositor
- Test what happens if you set the L2 gas limit too low
- Does the deposit fail gracefully? Can it be retried?

**Message Relay Timing**
- Deposits aren't instant—they take 1-5 minutes to relay
- Your tests must wait for confirmation, not just assume success
- Use the L2 SDK's message status tracking

**Failed Deposits**
- What if the L2 transaction runs out of gas?
- What if the L2 contract is paused?
- Ensure failed deposits don't lock funds permanently

## Testing Withdrawals (L2 → L1): The Hard Part

Withdrawals are where things get complex. On **Optimistic Rollups** (Optimism, Base, and to some extent Arbitrum), withdrawals have a mandatory **7-day challenge period** before they can be finalized on L1.

### Why the 7-Day Wait?

Optimistic Rollups use a "guilty until proven innocent" model:
- L2 transactions are assumed valid
- But anyone can challenge them with fraud proofs
- The 7-day window gives challengers time to act
- Only after 7 days can withdrawals be finalized on L1

This delay is **by design** and cannot be avoided in production. But in testing, you need to simulate it.

### The Withdrawal Flow

```
Day 0:   User initiates withdrawal on L2 (burns L2 tokens)
         ↓
Day 0-7: Challenge period (transaction batch submitted to L1)
         ↓
Day 7:   Withdrawal can be "proven" on L1 (proof submitted)
         ↓
Day 7+:  Withdrawal can be "finalized" on L1 (tokens released)
```

### The QA's Job: Time Manipulation

To test withdrawals, you must:
1. Initiate the withdrawal on L2
2. **Fast-forward time by 7 days** using Hardhat's time manipulation
3. Submit the withdrawal proof to L1
4. Finalize the withdrawal
5. Verify tokens are released

Here's how:

```javascript
describe('Bridge Withdrawals (L2 -> L1)', () => {
  it('should complete a full withdrawal after challenge period', async () => {
    const withdrawAmount = ethers.utils.parseEther('50');
    
    // STEP 1: Initiate withdrawal on L2
    const withdrawTx = await l2Bridge.connect(user).withdraw(
      l2Token.address,
      withdrawAmount,
      0, // L1 gas
      ethers.constants.AddressZero
    );
    
    const withdrawReceipt = await withdrawTx.wait();
    const withdrawalMessage = await getWithdrawalMessage(withdrawReceipt);
    
    console.log('Withdrawal initiated on L2');
    
    // STEP 2: Wait for L2 -> L1 message to be ready for relay
    // In production, this takes ~1 hour (when the batch is submitted to L1)
    await waitForMessageStatus(
      withdrawalMessage.messageNonce,
      MessageStatus.READY_FOR_RELAY
    );
    
    console.log('Withdrawal ready to prove on L1');
    
    // STEP 3: Fast-forward time to simulate the 7-day challenge period
    // This is the key difference from deposit testing
    const SEVEN_DAYS = 7 * 24 * 60 * 60;
    await ethers.provider.send('evm_increaseTime', [SEVEN_DAYS]);
    await ethers.provider.send('evm_mine'); // Mine a block to apply the time change
    
    console.log('Fast-forwarded 7 days (challenge period)');
    
    // STEP 4: Prove the withdrawal on L1
    // This submits the Merkle proof that the withdrawal happened on L2
    const proveTx = await l1Bridge.proveWithdrawalTransaction(
      withdrawalMessage.nonce,
      withdrawalMessage.sender,
      withdrawalMessage.target,
      withdrawalMessage.value,
      withdrawalMessage.gasLimit,
      withdrawalMessage.data,
      withdrawalMessage.proof // Merkle proof from L2 state
    );
    
    await proveTx.wait();
    console.log('Withdrawal proven on L1');
    
    // STEP 5: Finalize the withdrawal on L1
    // This actually releases the tokens
    const l1BalanceBefore = await token.balanceOf(user.address);
    
    const finalizeTx = await l1Bridge.finalizeWithdrawalTransaction(
      withdrawalMessage.nonce,
      withdrawalMessage.sender,
      withdrawalMessage.target,
      withdrawalMessage.value,
      withdrawalMessage.gasLimit,
      withdrawalMessage.data
    );
    
    await finalizeTx.wait();
    console.log('Withdrawal finalized on L1');
    
    // STEP 6: Verify tokens were released
    const l1BalanceAfter = await token.balanceOf(user.address);
    expect(l1BalanceAfter).to.equal(l1BalanceBefore.add(withdrawAmount));
    
    console.log('✅ Full withdrawal completed successfully');
  });
  
  it('should reject finalization before challenge period ends', async () => {
    // Initiate withdrawal
    const withdrawTx = await l2Bridge.withdraw(/* ... */);
    const withdrawalMessage = await getWithdrawalMessage(withdrawTx);
    
    // Prove immediately (should succeed)
    await l1Bridge.proveWithdrawalTransaction(/* ... */);
    
    // Try to finalize immediately (should fail)
    await expect(
      l1Bridge.finalizeWithdrawalTransaction(/* ... */)
    ).to.be.revertedWith('Challenge period not elapsed');
    
    // Fast-forward 6 days (still not enough)
    await ethers.provider.send('evm_increaseTime', [6 * 24 * 60 * 60]);
    await ethers.provider.send('evm_mine');
    
    await expect(
      l1Bridge.finalizeWithdrawalTransaction(/* ... */)
    ).to.be.revertedWith('Challenge period not elapsed');
    
    // Fast-forward 1 more day (now it should work)
    await ethers.provider.send('evm_increaseTime', [1 * 24 * 60 * 60]);
    await ethers.provider.send('evm_mine');
    
    await expect(
      l1Bridge.finalizeWithdrawalTransaction(/* ... */)
    ).to.not.be.reverted;
  });
  
  it('should handle multiple pending withdrawals correctly', async () => {
    // Initiate 3 withdrawals in sequence
    const withdrawal1 = await initiateWithdrawal(user1, '10');
    const withdrawal2 = await initiateWithdrawal(user2, '20');
    const withdrawal3 = await initiateWithdrawal(user3, '30');
    
    // Fast-forward past challenge period
    await ethers.provider.send('evm_increaseTime', [7 * 24 * 60 * 60]);
    await ethers.provider.send('evm_mine');
    
    // Finalize in different order
    await finalizeWithdrawal(withdrawal2); // user2 first
    await finalizeWithdrawal(withdrawal1); // user1 second
    await finalizeWithdrawal(withdrawal3); // user3 third
    
    // Verify all received correct amounts
    expect(await token.balanceOf(user1.address)).to.equal(/* ... */);
    expect(await token.balanceOf(user2.address)).to.equal(/* ... */);
    expect(await token.balanceOf(user3.address)).to.equal(/* ... */);
  });
});
```

### Critical Withdrawal Testing Scenarios

**1. Challenge Period Enforcement**
- Verify withdrawals cannot be finalized early
- Test boundary conditions (exactly 7 days, 7 days - 1 second, etc.)

**2. Replay Protection**
- Ensure a withdrawal can only be finalized once
- Test that replaying the finalization transaction fails

**3. Invalid Proofs**
- Submit fake Merkle proofs
- Verify they're rejected by the L1 bridge

**4. Failed Finalizations**
- What if the L1 contract is out of funds?
- What if the recipient is a contract that reverts?

**5. Partial Withdrawals**
- Can users withdraw in multiple smaller amounts?
- Are they charged L1 gas for each withdrawal?

## Understanding "Fast" vs. "Final" Transactions

One of the most confusing aspects of L2s for new developers and QAs is the concept of **transaction finality**. On Ethereum mainnet, finality is simple: once your transaction is included in a block and that block gets a few confirmations, it's final. On L2s, **there are multiple levels of finality**.

### The Three Stages of L2 Finality

**Stage 1: Sequencer Confirmation ("Soft Finality")**
- Your transaction is included in the L2 sequencer's mempool
- The sequencer executes it and returns a receipt
- **Time**: Seconds
- **Security**: Low (trust the sequencer)

**Stage 2: L1 Data Availability ("Safe Finality")**
- Your transaction's data is posted to Ethereum L1
- Anyone can reconstruct the L2 state from this data
- **Time**: Minutes to hours (depends on batch submission frequency)
- **Security**: Medium (data is on L1, but state isn't proven)

**Stage 3: L1 State Finality ("Hard Finality")**
- For Optimistic Rollups: 7 days after challenge period expires
- For ZK Rollups: When the validity proof is verified on L1
- **Time**: 7 days (Optimistic) or ~1 hour (ZK)
- **Security**: High (secured by Ethereum's consensus)

### The QA Takeaway: When to Wait for Finality

As a QA, you need to determine **which level of finality** your dApp requires for each operation.

**Operations That Need Hard Finality:**
- ❌ Large financial transfers (> $10k)
- ❌ Cross-chain messages with critical state changes
- ❌ Irreversible operations (e.g., burning NFTs)

**Operations That Can Use Soft Finality:**
- ✅ UI updates and display logic
- ✅ Small value transfers
- ✅ Gaming and social actions

### Testing Finality Levels

```javascript
describe('Finality Levels', () => {
  it('should receive sequencer confirmation instantly', async () => {
    const startTime = Date.now();
    
    const tx = await contract.connect(user).transfer(recipient, amount);
    const receipt = await tx.wait();
    
    const endTime = Date.now();
    const confirmationTime = endTime - startTime;
    
    // Sequencer confirmation should be < 5 seconds
    expect(confirmationTime).to.be.lessThan(5000);
    expect(receipt.status).to.equal(1);
    
    console.log(`Sequencer confirmation: ${confirmationTime}ms`);
  });
  
  it('should wait for L1 data availability before critical operation', async () => {
    // Perform a critical operation
    const tx = await bank.connect(user).withdraw(largeAmount);
    const receipt = await tx.wait();
    
    // Don't trust sequencer confirmation—wait for L1 batch submission
    const l1Batch = await waitForL1Batch(receipt.blockNumber);
    
    // Now verify the operation is included in L1 data
    const l1Tx = await l1Provider.getTransaction(l1Batch.transactionHash);
    expect(l1Tx).to.exist;
    
    console.log('L1 data availability confirmed');
    
    // Only now should the UI show "withdrawal successful"
  });
  
  it('should test state rollback if sequencer is malicious', async () => {
    // This is an advanced test that simulates a malicious sequencer
    // The sequencer includes your transaction, then reorganizes blocks
    
    const tx1 = await contract.transfer(recipient1, amount);
    await tx1.wait();
    
    // Sequencer appears to confirm...
    let balance = await contract.balanceOf(recipient1);
    expect(balance).to.equal(amount);
    
    // But then sequencer reorgs (simulated by reverting the state)
    await revertToSnapshot(); // Hardhat snapshot
    
    // Your "confirmed" transaction is now gone!
    balance = await contract.balanceOf(recipient1);
    expect(balance).to.equal(0);
    
    console.log('⚠️ Sequencer reorg detected - transaction reverted');
  });
});
```

### Best Practices for Testing Finality

1. **Don't Trust Sequencer Receipts for High-Value Ops**: Always wait for L1 batch submission
2. **Test Reorganization Scenarios**: Simulate what happens if the sequencer reorders blocks
3. **Monitor L1 Batch Submission Frequency**: If batches are submitted every 10 minutes, your "safe" finality is at least 10 minutes
4. **Implement Timeouts**: If L1 finality is required, set appropriate timeouts (e.g., 1 hour for ZK, 7+ days for Optimistic)

## Testing New Failure Modes: Beyond Smart Contracts

On Ethereum mainnet, your biggest concerns are smart contract bugs and gas costs. On L2s, you have **entirely new categories of failure** to test for.

### Failure Mode #1: Sequencer Downtime

Most L2s use a **centralized sequencer** to order transactions. This is a single point of failure.

**What Happens When the Sequencer Goes Down?**
- New transactions cannot be submitted to L2
- Existing transactions are "frozen" until the sequencer returns
- On some L2s, there's a "force inclusion" mechanism to bypass the sequencer (but it's slow and expensive)

**The QA's Responsibility:**

You need to test your dApp's behavior when the sequencer is unavailable.

```javascript
describe('Sequencer Failure Scenarios', () => {
  it('should handle sequencer downtime gracefully', async () => {
    // Simulate sequencer downtime by refusing new transactions
    await stopSequencer(); // Custom test helper
    
    // Attempt a transaction
    const txPromise = contract.connect(user).transfer(recipient, amount);
    
    // Transaction should be stuck in mempool, not fail immediately
    // In reality, the wallet/RPC will timeout after ~60 seconds
    
    await expect(txPromise).to.be.rejectedWith('Sequencer unavailable');
    
    // Verify the dApp UI shows an appropriate message
    const errorState = await dApp.getConnectionStatus();
    expect(errorState).to.equal('SEQUENCER_OFFLINE');
  });
  
  it('should enable read-only mode during sequencer downtime', async () => {
    await stopSequencer();
    
    // Writes should fail
    await expect(contract.write()).to.be.rejected;
    
    // Reads should still work (querying L1 state or cached L2 state)
    const balance = await contract.balanceOf(user.address);
    expect(balance).to.exist;
    
    // UI should clearly indicate read-only mode
    const mode = await dApp.getMode();
    expect(mode).to.equal('READ_ONLY');
  });
  
  it('should use force inclusion if available', async () => {
    // Some L2s allow users to submit transactions directly to L1
    // which are then force-included in the L2 chain
    
    await stopSequencer();
    
    // Submit transaction via L1 force inclusion
    const l1Tx = await l1Contract.forceInclusion(
      l2ContractAddress,
      calldata,
      { value: ethers.utils.parseEther('0.01') } // High L1 gas cost
    );
    
    await l1Tx.wait();
    
    // Wait for L2 to process the force-included transaction
    // This can take 10+ minutes
    await waitForL2ProcessingOfL1Tx(l1Tx.hash);
    
    // Verify the transaction was executed on L2
    const receipt = await l2Provider.getTransactionReceipt(/* ... */);
    expect(receipt.status).to.equal(1);
  });
});
```

**User Experience Considerations:**
- Does your dApp display a "Network Unavailable" message?
- Do pending transactions show a spinner, or do they fail silently?
- Can users still view their balances and history?

### Failure Mode #2: L1 Gas Spikes

L2s inherit security from Ethereum L1 by posting data and proofs to L1. But this means **L1 gas costs directly impact L2 operations**.

**How L1 Gas Affects L2:**
- **Batch Submission Costs**: The L2 sequencer pays L1 gas to post batches
- **Withdrawal Finalization**: Users pay L1 gas to prove and finalize withdrawals
- **Cross-Chain Messages**: Any L1 ↔ L2 interaction involves L1 gas

**When L1 gas spikes (e.g., during an NFT mint or network congestion):**
- L2 transaction fees increase (to cover L1 data posting costs)
- Withdrawals become prohibitively expensive
- Batch submission may slow down (sequencer waits for cheaper gas)

**Testing L1 Gas Impact:**

```javascript
describe('L1 Gas Spike Scenarios', () => {
  it('should increase L2 fees when L1 gas is high', async () => {
    // Record baseline L2 fee with normal L1 gas
    const normalL1Gas = await l1Provider.getGasPrice();
    const normalL2Fee = await estimateL2TransactionFee(tx);
    
    console.log(`Normal L1 gas: ${ethers.utils.formatUnits(normalL1Gas, 'gwei')} gwei`);
    console.log(`Normal L2 fee: ${ethers.utils.formatEther(normalL2Fee)} ETH`);
    
    // Simulate L1 gas spike (e.g., 500 gwei)
    await setL1GasPrice(ethers.utils.parseUnits('500', 'gwei'));
    
    const spikedL2Fee = await estimateL2TransactionFee(tx);
    
    console.log(`Spiked L2 fee: ${ethers.utils.formatEther(spikedL2Fee)} ETH`);
    
    // L2 fee should increase proportionally
    expect(spikedL2Fee).to.be.greaterThan(normalL2Fee.mul(3));
    
    // Verify dApp warns users about high fees
    const warning = await dApp.getFeeWarning();
    expect(warning).to.include('High network fees');
  });
  
  it('should make withdrawals expensive during L1 gas spikes', async () => {
    // Normal withdrawal finalization cost
    const normalGasCost = await estimateWithdrawalFinalizationCost();
    expect(normalGasCost).to.be.lessThan(ethers.utils.parseEther('0.01'));
    
    // Spike L1 gas to 1000 gwei
    await setL1GasPrice(ethers.utils.parseUnits('1000', 'gwei'));
    
    const spikedGasCost = await estimateWithdrawalFinalizationCost();
    expect(spikedGasCost).to.be.greaterThan(ethers.utils.parseEther('0.05'));
    
    // This could cost $100+ at high ETH prices!
    console.log(`Withdrawal cost during spike: $${(spikedGasCost * ethPrice).toFixed(2)}`);
    
    // dApp should warn users: "Withdrawal will cost $X in gas. Wait for lower fees?"
  });
  
  it('should delay batch submissions when L1 gas is too high', async () => {
    // Sequencers often have a max gas price they're willing to pay
    const maxGasPrice = await sequencer.getMaxL1GasPrice();
    
    // Spike L1 gas above this threshold
    await setL1GasPrice(maxGasPrice.mul(2));
    
    // Submit some L2 transactions
    await contract.transfer(recipient, amount);
    
    // Verify that the batch is NOT submitted immediately
    const batchBefore = await getLatestBatchNumber();
    
    await waitForSeconds(120); // Wait 2 minutes
    
    const batchAfter = await getLatestBatchNumber();
    expect(batchAfter).to.equal(batchBefore); // No new batch
    
    console.log('Batch submission delayed due to high L1 gas');
    
    // Return L1 gas to normal
    await setL1GasPrice(normalGasPrice);
    
    // Now the batch should be submitted
    await waitForSeconds(60);
    const batchFinal = await getLatestBatchNumber();
    expect(batchFinal).to.be.greaterThan(batchBefore);
  });
});
```

**UX Best Practices:**
- Display estimated L1 + L2 costs separately in the UI
- Warn users when withdrawal costs exceed a threshold (e.g., $20)
- Allow users to queue withdrawals and finalize later when gas is cheaper

### Failure Mode #3: State Divergence (Optimistic vs. ZK Rollups)

On **Optimistic Rollups**, there's a risk (however small) that the L2 state could diverge from what L1 thinks is correct—if a fraud proof is successfully submitted.

**Testing Fraud Proof Scenarios:**

```javascript
describe('Fraud Proof Scenarios (Advanced)', () => {
  it('should revert L2 state if fraud proof is valid', async () => {
    // This is a complex scenario where:
    // 1. The L2 sequencer posts an invalid state root to L1
    // 2. A challenger submits a fraud proof
    // 3. The L1 contract accepts the proof and reverts the L2 state
    
    // Submit an invalid transaction on L2 (e.g., double-spend)
    const invalidTx = await submitInvalidL2Transaction();
    
    // Sequencer posts this to L1 (in a real attack)
    await sequencer.submitBatch(invalidStateRoot);
    
    // Challenger detects the invalid state
    const fraudProof = await generateFraudProof(invalidTx);
    
    // Submit fraud proof to L1
    const challengeTx = await l1Contract.submitFraudProof(fraudProof);
    await challengeTx.wait();
    
    // L1 contract should slash the sequencer and revert the batch
    const newStateRoot = await l1Contract.getStateRoot();
    expect(newStateRoot).to.not.equal(invalidStateRoot);
    
    // The invalid transaction should be reverted on L2
    const receipt = await l2Provider.getTransactionReceipt(invalidTx.hash);
    expect(receipt).to.be.null; // Transaction no longer exists
    
    console.log('✅ Fraud proof accepted, invalid state reverted');
  });
});
```

**Note**: Testing fraud proofs requires deep integration with the L2's challenge mechanism and is typically only done by the L2 protocol team, not dApp developers. But understanding the concept is critical for QA.

## The New Testing Mindset: You're Testing a System, Not a Contract

Testing on L2 requires a **fundamental mindset shift**. You're no longer just testing whether `transfer()` works correctly. You're testing a **complex distributed system** with multiple moving parts:

### The Old (L1) Mindset
- ✅ Does this function return the right value?
- ✅ Does it revert on invalid input?
- ✅ Does it emit the correct events?
- ✅ Is it gas-efficient?

### The New (L2) Mindset
- ✅ Does this work across two blockchains (L1 and L2)?
- ✅ What happens if the sequencer is down?
- ✅ How long does finality actually take?
- ✅ Can users afford to withdraw during high L1 gas?
- ✅ What's the failure mode if a fraud proof is submitted?
- ✅ How does the dApp handle delayed messages?

### Your L2 Testing Checklist

Use this checklist for every L2 dApp you test:

**Bridge Operations:**
- [ ] Deposits from L1 to L2 work correctly
- [ ] Withdrawals from L2 to L1 complete after challenge period
- [ ] Failed deposits don't lock funds
- [ ] Multiple pending withdrawals are tracked correctly
- [ ] Replay attacks on withdrawals are prevented

**Finality and Timing:**
- [ ] Critical operations wait for L1 finality
- [ ] UI clearly indicates transaction status (sequenced vs. final)
- [ ] Timeouts are set appropriately (7+ days for withdrawals)
- [ ] Sequencer reorgs are handled gracefully

**Failure Modes:**
- [ ] Sequencer downtime triggers read-only mode
- [ ] High L1 gas is detected and users are warned
- [ ] Batch submission delays are handled
- [ ] Force inclusion mechanism works (if available)

**User Experience:**
- [ ] Fee estimates include L1 data costs
- [ ] Withdrawal costs are clearly displayed
- [ ] "Network Unavailable" messages are shown when appropriate
- [ ] Pending cross-chain messages have clear status indicators

## Real-World Example: Testing a Cross-Chain DEX

Let's put it all together with a real-world scenario: testing a decentralized exchange that operates on both L1 and L2.

### The Scenario

Your dApp is a DEX where:
- Users can deposit tokens on L1
- Tokens are bridged to L2 for cheap, fast trading
- Users can withdraw profits back to L1

### The Test Suite

```javascript
describe('Cross-Chain DEX: Full Integration Test', () => {
  it('should handle the complete user journey', async () => {
    // PHASE 1: Deposit to L2
    console.log('PHASE 1: Depositing tokens from L1 to L2...');
    
    const depositAmount = ethers.utils.parseEther('1000'); // 1000 USDC
    await token.approve(l1Bridge.address, depositAmount);
    await l1Bridge.depositERC20(token.address, l2Token.address, depositAmount, 200000, '0x');
    
    await waitForL2Message(); // Wait ~2 minutes
    
    const l2Balance = await l2Token.balanceOf(user.address);
    expect(l2Balance).to.equal(depositAmount);
    console.log('✅ Deposit complete');
    
    // PHASE 2: Trade on L2
    console.log('PHASE 2: Trading on L2 DEX...');
    
    await l2Dex.swap(l2Token.address, l2Weth.address, depositAmount);
    
    const wethBalance = await l2Weth.balanceOf(user.address);
    expect(wethBalance).to.be.greaterThan(0);
    console.log(`✅ Swapped 1000 USDC for ${ethers.utils.formatEther(wethBalance)} WETH`);
    
    // PHASE 3: Withdraw profits to L1
    console.log('PHASE 3: Withdrawing WETH from L2 to L1...');
    
    const withdrawAmount = wethBalance;
    await l2Bridge.withdraw(l2Weth.address, withdrawAmount, 0, '0x');
    
    // Wait for batch submission
    await waitForL1Batch();
    console.log('✅ Withdrawal initiated, waiting for challenge period...');
    
    // Fast-forward 7 days
    await ethers.provider.send('evm_increaseTime', [7 * 24 * 60 * 60]);
    await ethers.provider.send('evm_mine');
    console.log('✅ Challenge period complete');
    
    // Prove and finalize
    await l1Bridge.proveWithdrawalTransaction(/* ... */);
    await l1Bridge.finalizeWithdrawalTransaction(/* ... */);
    
    const l1WethBalance = await wethToken.balanceOf(user.address);
    expect(l1WethBalance).to.equal(withdrawAmount);
    console.log('✅ Withdrawal finalized on L1');
    
    console.log('\n🎉 FULL CROSS-CHAIN DEX TEST PASSED');
  });
});
```

This single test validates:
- Bridge deposits (L1 → L2)
- L2 trading functionality
- Bridge withdrawals (L2 → L1)
- Challenge period timing
- Proof submission and finalization

## Conclusion: The L2 Testing Paradigm

Testing on Layer 2 is not just a minor extension of L1 testing—it's a **completely different discipline**. You're no longer testing isolated smart contracts; you're testing **distributed systems** with bridges, sequencers, time delays, and cross-chain message passing.

### The Core Principles

1. **Think Multi-Chain**: Every operation involves two blockchains (L1 and L2)
2. **Test Time Delays**: Challenge periods, batch submissions, and message relays all take time
3. **Anticipate Failures**: Sequencers go down, L1 gas spikes, and messages get stuck
4. **Wait for Finality**: Sequencer receipts are not enough for critical operations
5. **Monitor Costs**: L1 gas directly impacts L2 fees and withdrawal costs

### Your Path Forward

1. **Master the Basics**: Understand how Optimistic and ZK Rollups work
2. **Learn the SDKs**: Get comfortable with the Optimism and Arbitrum SDKs
3. **Build a Test Suite**: Implement comprehensive bridge and finality tests
4. **Automate Everything**: L2 testing is too complex for manual verification
5. **Stay Updated**: L2 protocols are rapidly evolving—follow their documentation

### Final Thoughts

L2s represent the future of Ethereum scaling. As a QA engineer, your role is to ensure that this future is **secure, reliable, and user-friendly**. The complexity of L2 systems means there are more ways for things to go wrong—but also more opportunities for rigorous testing to prevent catastrophic failures.

The bridge hacks that cost users hundreds of millions of dollars? **Better testing could have prevented them.**

The withdrawal delays that frustrate users? **Better UX testing could have warned them.**

The sequencer downtimes that freeze applications? **Better failure mode testing could have prepared for them.**

You're not just testing smart contracts. You're testing the infrastructure that will power the next generation of decentralized applications. **Test thoroughly. Test creatively. Test like the security of millions of dollars depends on it—because it does.**
